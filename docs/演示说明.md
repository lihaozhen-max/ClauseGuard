# ClauseGuard 演示说明（Runbook）

> 面向"现场演示 / 录屏 / 答辩"的操作手册。目标：**10 分钟内**把九步业务闭环、
> 异常阻塞与人工重试、全链路日志、规则维护四件事演示完。
> 规范依据：`docs/SPEC.md` §6（业务流程）、§13（AC01–AC19）；配套 `docs/验收对照表.md`。

---

## 0. 开演前 5 分钟准备

按顺序起四个进程（每个都开独立终端）：

| # | 进程 | 命令 | 就绪标志 |
|---|---|---|---|
| 1 | MySQL | `cd database; docker compose --env-file ../.env up -d` | `docker compose ps` 显示 `(healthy)` |
| 2 | 模拟审批系统 | `uv run --project backend uvicorn --app-dir mock-approval-system main:app --host 127.0.0.1 --port 8100` | `curl http://127.0.0.1:8100/health` → `approvals: 5` |
| 3 | 工具服务 | `cd backend; uv run uvicorn app.main:app --host 127.0.0.1 --port 8000` | `curl http://127.0.0.1:8000/health` → `"connected":true` |
| 4 | 调用端 | `cd frontend-or-client; npm run dev` | 浏览器打开 <http://127.0.0.1:5173> |

**首演前务必预热 OCR**：第一次 OCR 会联网下载 PaddleOCR 模型（数百 MB）。
先随便找一份扫描件跑一次，或直接执行：

```powershell
uv run --project backend python -c "from paddleocr import PaddleOCR; PaddleOCR(lang='ch', use_doc_orientation_classify=False, use_doc_unwarping=False, use_textline_orientation=False, enable_mkldnn=False)"
```

> 若不预热，AC05 的现场演示会卡在下载界面。已预热时单页 OCR 约 **60–77 秒**（CPU），
> 演示前先说明这一点，避免观众以为卡死。

**LLM 可选**：`.env` 里 `LLM_ENABLED=true` 走真实 DeepSeek（语义规则 R004/R009 有明确判定）；
置 `false` 则降级为"纯规则 + 模板摘要"，**闭环照样跑通**（LM-18）。
网络不稳时建议演示降级模式，更可控。

## 1. 一键复现演示（命令行走完 AC19 + AC16/AC17）

```powershell
cd ClauseGuard
uv run --project backend python scripts/demo_closed_loop.py --reset --all
```

脚本会清库、拉取、把 AP-001 走完九步闭环，再把 AP-004 演一遍"附件缺失 → 补齐 → 人工重试"，
逐条打印判据的实测值，最后给出 `演示结果：N/N 项判据通过`。

常用变体：

```powershell
… demo_closed_loop.py                 # 只跑 AC19（AP-001）
… demo_closed_loop.py --retry         # 只跑 AC16 → AC17（AP-004）
… demo_closed_loop.py --reset --all   # 清库后全跑（推荐现场用）
```

> `--retry` 会临时把 `AP-002_服务合同.pdf` 复制成 AP-004 声明的附件名（模拟"审批人补交合同"），
> 演示结束**自动删除**，恢复"附件缺失"基线。

## 2. 界面演示脚本（对着浏览器讲）

代码里已经把每一步做成独立路由，直接切标签即可，不必来回搜索。

### 2.1 待办调用（FR-UI-01）

1. 打开 <http://127.0.0.1:5173> → 默认就是**待办任务**列表；
2. 点 **「拉取待办（IF-10）」** → 提示"新增 5 条"；
3. **再点一次** → 提示"新增 0 条、更新 5 条"，列表里 `task_id` 不变 →
   讲 **AC02 幂等去重**（唯一索引兜底，并发双拉也不会产生第二个任务）。

### 2.2 完整闭环（AC19）

以 AP-001 为例，在任务详情页依次点五个标签：

| 标签 | 讲什么 |
|---|---|
| **详情查看** | 审批基本信息、**表单数据（来源：审批系统 IF-02）**、附件元数据 + SHA-256。顺带讲 FR-SYS-02：合同正文存私有目录，**不提供任何直链** |
| **解析结果** | 8 条基本信息 + 8 条条款，每条都有原文片段与位置（§2.6）；`missing` 行橙色底色。点 **「触发解析（IF-14）」** 现场跑一次 |
| **规则命中** | 整体风险「高」红块 → 讲 **NF-10 三色**；11 条规则明细含证据原文、`第X页 第Y段`、建议；关注点 5 条。点 **「触发审查（IF-16）」** 现场跑一次 |
| **结果处理** | §4.6.1 模板评论正文、回写状态/时间/备注号、回写历史。点 **「回写评论（IF-17）」** → 成功；**再点一次** → 提示"已回写过，直接返回既有结果" → 讲 **幂等（FR-COM-06）** |
| **任务日志** | 顶部 8 类覆盖条（文本型合同是 7 类，缺 `ocr` 属**预期**）、底部逐条日志含耗时 |

### 2.3 异常阻塞与人工重试（AC16 → AC17）

打开 AP-004：页头黄色告警 **「任务已阻塞于 parsing 阶段：CONTRACT_ATTACHMENT_MISSING」**。

1. 讲 ST-01：失败**不删数据**、记录断点 `blocked_stage` + `error_code`（NF-04 可恢复）；
2. 点 **「触发解析」** 复现一次 404（附件确实不存在）；
3. 到 `sample_contracts/` 里复制一份 PDF 并改名成 `AP-004_办公用品采购合同.pdf`（模拟补交）；
4. 回到页面点 **「人工重试（IF-20）」** → 任务从 `parsing` 续跑并 `done`，
   页头出现 **「已重试 1 次」**，任务日志里多出一条 `人工重试`。

### 2.4 全链路日志（AC18）

打开 AP-003（扫描件）的**任务日志**页：先点解析（约 60–77s），日志里会出现 `OCR 识别`，
8 类覆盖条变成 **8/8 全绿** → 这正是 AC18 要的证据。

### 2.5 规则维护（FR-UI-08 / IF-21）

打开左侧 **规则维护**：

1. 把 R005（管辖地风险）的开关**关掉** → 提示"已停用，下次审查起生效"；
2. 回到 AP-001 点 **重新触发审查** → R005 不再参与判定 → 讲 **FR-RULE-01（只有启用规则参与审查）**；
3. 把 R001 的等级从「中」改成「高」，在**编辑**里改建议文案 → 讲这是 FR-UI-08 的三件事；
4. 强调：改规则**只影响之后的审查**，已入库的命中是当时的快照（FR-RULE-09）——历史不会被改判；
5. 演示完**把规则改回**（或执行 `database/seed_rules.sql`，它按 `rule_code` 幂等 upsert）。

## 3. 常见提问与一句话回答

| 提问 | 回答 |
|---|---|
| 系统会不会替人做审批决定？ | 不会。SPEC 开头即声明：只做风险识别与解释，评论里固定带免责声明，最终结论由审批人判断 |
| LLM 会不会编造证据？ | 不会。模型只做"是/否 + 理由"，证据必须通过"是否为合同原文连续子串"的回验（PS-10），回验不过就降级为 `uncertain` |
| 风险等级是 LLM 定的吗？ | 不是。等级由 **RL-AGG** 算法汇总，`uncertain`/`miss` 不参与计算（RL-AGG-01），LLM 只参与三处语义判断（LM-01…LM-03） |
| 重复拉取会不会产生两条任务？ | 不会。`instance_id` 唯一索引 + `ON DUPLICATE KEY UPDATE`（AC02 实测） |
| 评论会不会写两遍？ | 不会。幂等键 `SHA-256(instance_id:review_id)` + 唯一索引（AC15 实测） |
| 审批系统挂了会怎样？ | 任务进 `blocked` 并记断点；补好后 `retry` 从断点续跑。只有 LLM 失败**不**阻塞任务，只做降级 |
| 合同附件能直接下载吗？ | 不能，且是有意为之：不挂静态路由（FR-SYS-02），页面只展示元数据 |
| 日志里会不会泄漏密钥？ | 不会。日志经过脱敏过滤器 + 截断 ≤500 字符（FR-LOG-03/04），并有测试守着 |

## 4. 演示后的收尾

```powershell
# 停掉三个进程（各自终端 Ctrl+C），停数据库
cd database; docker compose --env-file ../.env down      # 加 -v 会连数据一起删
```

若演示中改过规则，执行 `database/seed_rules.sql` 恢复基线；若想把演示数据清干净，
用 `scripts/demo_closed_loop.py --reset` 的清理逻辑（或直接跑一次 `pytest`，它会在会话开始时清空业务表）。

## 5. 自动化证据（答辩/复核时可现场跑）

如果评委想"自己看证据"而不是听讲解，按下面三条命令跑，全部可复现：

```powershell
# ① 全量回归（约 4~5 分钟，含真实 OCR）
cd backend; uv run pytest -q

# ② 浏览器端到端：用真实 Chrome 点界面（需 8000 与 5173 已在跑，约 20 秒）
uv run pytest -q -m ui

# ③ 性能基线：接口耗时 / 数据量增长 / 8 路并发（合成数据测完自动删）
cd ..; uv run --project backend python scripts/bench.py
```

逐条 AC 对应的用例与截图见 `docs/验收对照表.md`；加固项的实测结论（含两个被测试抓出并修复的并发缺陷）
见 `docs/M7-验收记录.md` §7。
