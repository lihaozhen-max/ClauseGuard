## 3. 关键发现与实现决策

### 3.1 【R-01】技术栈照设计 §11 落地，但**刻意不加多余依赖**

设计 §11 已指定 **Vue 3 + Element Plus + Vite**，因此这不是"新增技术选型"，而是既定方案的实施。
即便如此，仍按最小面引入：

| 依赖 | 用途 | 为什么不用替代品 |
|---|---|---|
| `vue` / `vue-router` | 框架与路由 | 设计指定 |
| `element-plus` + `@element-plus/icons-vue` | UI 组件与图标 | 设计指定 |
| `vite` / `@vitejs/plugin-vue` | 构建 | 设计指定 |
| `typescript` / `vue-tsc` | 类型检查 | 与后端 pydantic 口径对齐，能在编译期发现字段名写错 |

**没有引入**：`axios`（用原生 `fetch` 足够）、`pinia`（只有一个共享上下文，`provide/inject` 够用）、
`unplugin-auto-import` / `unplugin-vue-components`（Element Plus 全量引入换取零构建期插件配置）、
任何端到端测试框架（见 M6-C）。

后端本次**没有新增任何 Python 依赖**。

### 3.2 【R-02】用 Vite 代理打通跨域，而不是给后端加 CORS

前端 `npm run dev`（5173）把 `/api` 反向代理到 `127.0.0.1:8000`。这样做的好处是：

1. 浏览器侧同源，**后端一行 CORS 中间件都不用加**——不扩大接口面，也不给生产配置留隐患；
2. `X-API-Key` 仍然由前端照常携带，鉴权链路与生产完全一致（FR-SYS-03）。

代价是"生产构建产物不能直接双击打开"，需要同源部署或反代——本项目交付形态是"两个进程 + 内网"，
这一点已写进 `frontend-or-client/README.md`。

### 3.3 【R-03】FR-SYS-02 决定了"详情页不能给附件直链"

SPEC FR-SYS-02 要求合同附件**禁止**通过任何静态路由暴露。因此详情页的附件区**只展示元数据**
（文件名、类型、大小、SHA-256、下载状态），不提供预览/下载链接，并在页面上写明原因。
这是规范约束下的**正确**做法，但它确实让"看合同原文"只能通过解析结果页的 `source_text`/`position`
间接完成——这是本项目定位（审查辅助，不做合同阅读器）的必然结果。

### 3.4 【R-04】`X-API-Key` 的存放方式：构建期变量 + 浏览器 localStorage

调用端跑在浏览器里，密钥对使用者必然可见。真正的边界是"仅内网可达 + 后端校验"，不是"前端藏密钥"。
因此实现为：优先用构建期 `VITE_INTERNAL_API_KEY`，留空则在页面右上角"接口密钥"对话框填写并存入
localStorage，**演示时换后端不必重新构建**。

联调时在 `frontend-or-client/.env.local` 写了本机密钥（该文件被 `.gitignore` 忽略，不入库），
并在 `.env.example` 中说明了用法。

### 3.5 【R-05】五个模块做成"任务内的子路由"，而不是一个页面的五段折叠面板

`/tasks/:id/{detail,parse,review,result,logs}` 各是一个真实路由（可直达、可刷新、可分享链接），
外壳 `TaskLayout` 负责页头状态与 Tab。这样：

- FR-UI-07 的"任务日志查看**页**"是真的一个页面，不是折叠块；
- AC17/AC18 截图可以直接给 URL；
- 页头状态是"活的"：任一模块触发的解析/审查/重试都会 `reload()` 让 `blocked`、`retry_count` 立即同步。

### 3.6 【R-06】规则变更**不回改**历史命中

`rule_hits` 存的是命中时的等级与建议**快照**（FR-RULE-09），所以规则维护页只影响**之后**的审查。
页面顶部把这句话明写出来，避免使用者误以为"改了等级，历史任务的风险等级也会跟着变"。

### 3.7 【R-07】NF-10 的"三色"不只靠颜色

风险等级同时给出：色块（绿/橙/红）+ 中文（低/中/高）+ 等级文字。规则明细表里还额外用
`el-tag` 的 `effect="dark"` 加粗。理由很直接：色觉障碍用户与黑白打印场景下，只靠颜色的区分等于没有区分。

同理，解析结果的 `missing`/`failed` 除底色外还带状态标签文字。

### 3.8 【R-08】文本型合同只有 7 类日志，页面必须说清这是**预期**

AP-001/AP-002 是文本型 PDF，没有 OCR 环节，因此 `log_types` 只有 7 类。
日志页在缺项提示里直接写明"缺 `ocr` 属预期语义；扫描件走完整闭环时 8 类应齐备"——
否则第一次看到"缺少 OCR 识别"的人会误判为缺陷。

## 5. 需要知悉的偏离与补充（请确认）

| 编号 | 内容 | 理由 |
|---|---|---|
| **M6-A** | 新增补充错误码 **`RULE_NOT_FOUND`(404)** | SPEC §5.4 的 12 个规范码只覆盖"审批实例不存在"，没有"规则不存在"。直接复用 `APPROVAL_NOT_FOUND` 会让规则维护页的 404 语义被误读，故按 M0-C 的先例补一个码，并在 `errors.py` 中注明来源 |
| **M6-B** | IF-21 的修改接口落成 **`PUT /api/rules`**，`rule_id` 置于请求体 | SPEC §5.2 的"路径"列对 IF-21 三种方法统一写作 `/api/rules`，未给路径参数位。为**不改动规范表**，照字面实现；若更希望 RESTful 风格，可改为 `PUT /api/rules/{rule_id}`（前后端各改一处） |
| **M6-C** | 前端**不做**端到端自动化测试，改用 headless Chrome 手动渲染断言（§4.3） | 引入 Playwright/Cypress 会带来浏览器二进制与大量新增依赖，超出 M6 必要范围。当前以"typecheck + build + 19 模块编译 + 7 页面真实渲染断言"作为回归手段；演示前的人工核对仍在 M7 保留 |
| **M6-D** | 规则维护页不做权限分级 | SPEC/PRD 未要求管理员角色体系，内部接口统一由 `X-API-Key` 保护（FR-SYS-03）。若后续需要真正的"管理员"，应引入身份体系而非前端隐藏按钮 |
