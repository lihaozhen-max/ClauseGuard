## 3. 关键实现决策

### 3.1 IF-01 采用**两阶段事务**（本里程碑最重要的修正）

最初把"拉取 + upsert + 回读 + 落日志"放在一个事务里，测试暴露出两个**真实缺陷**：

1. **可见性缺陷**：并发双拉时，后到事务在 `ON DUPLICATE KEY UPDATE` 分支若未产生实际变更
   （本系统按 FR-APP-05 不更新任务态字段，重复拉取时值往往相同），该行不会被归入它自己的事务；
   MySQL 默认 REPEATABLE READ 下，其后用**普通快照读**回读 `task_id` 就看不到另一事务刚提交的行
   → `KeyError: 'AP-TEST-0001'`。
2. **改用 `SELECT ... FOR UPDATE` 后死锁**：把可见性问题换成了
   `asyncmy.errors.OperationalError: (1213, 'Deadlock found when trying to get lock')`，
   因为同一事务内既做 `INSERT ... ON DUPLICATE KEY UPDATE` 又做加锁读，锁范围与持锁时间都被放大。

最终实现为**两个短事务 + HTTP 调用在事务之外**：

```
HTTP 拉取（不开事务）
   ↓
阶段 1 写事务：幂等 upsert（SELECT 判 dedup → INSERT...ODKU / UPDATE）→ commit
   ↓
阶段 2 读事务：回读权威 task_id/task_status → 写 log_type=pull 日志 → commit
```

阶段 2 是新事务，快照天然包含全部已提交数据，因此既拿到权威 `task_id`，又**不需要任何加锁读**。

> **并发死锁仍可能发生**（`INSERT ... ON DUPLICATE KEY UPDATE` 在更高并发下的固有风险）：
> 本里程碑用 8 轮重复跑并发用例未复现。自动重试（1213/1205）属于任务级异常恢复范畴，
> 与 M5 的人工重试一并设计，此处**不**引入未经验证的重试逻辑。

### 3.2 去重以唯一索引为最终保障（FR-APP-03）

应用层 `SELECT` 只用于判定 `dedup=created/updated`，**不承担**唯一性职责；
新增走 `INSERT ... ON DUPLICATE KEY UPDATE`，并发下后到者自动落到更新分支。
`uk_approval_tasks_instance_id` 是唯一防线，`test_concurrent_double_pull_creates_single_task` 直接验证之。

### 3.3 测试策略：ASGI 内存传输 + 真机双进程各管一半

| 手段 | 覆盖什么 | 为什么 |
|---|---|---|
| `httpx.ASGITransport(app=mock_app)` | 完整 HTTP 语义（状态码、404、文件流）**+** 真实 MySQL | 快、稳、可重复；不必为跑测试拉进程 |
| 真机双进程（8100 + 8000） | **FR-SYS-01 的进程边界**、uvicorn 装配、跨进程网络 | 内存传输天然覆盖不到"是否真的能独立部署" |

两者都在 M1 跑过（证据见 §4）。

### 3.4 样例合同"一行一段、不折行"

样例 PDF 由 `generate_samples.py` 用 PyMuPDF 内置中文字体 `china-s` 渲染。
文本源刻意**每行 ≤ 单行宽度**，生成器对超长行**报错退出**而不是静默折行——因为一旦折行，
抽取出的句子会被换行符切断，M2 的 `position`（第 N 页 第 M 段）与 PS-10 证据子串校验都会失准。
实测三条关键句（R001/R003/R005 的正例）在 AP-001 抽取文本中是**精确连续子串**。

### 3.5 其他口径

- **Mock 鉴权**：SPEC 未直接要求，但 CF-06 明确"工具服务 → 审批系统的鉴权"存在，故 Mock 校验
  `X-API-Key == APPROVAL_API_KEY`，缺失/错误 → 401。
- **Mock 第 5 个接口**：`GET /approvals/{instance_id}/comments` 为**辅助接口**（不属于 FR-MOCK-01 的 4 个必需接口），
  供 AC15「审批系统侧出现该评论」核对，不可写。
- **任务不存在**沿用 `404 + APPROVAL_NOT_FOUND`，不新增业务错误码（理由见 `docs/接口说明.md` §3）。
- **`expected_results.json` 单一来源**：由 `seed.py` 导出，避免样例期望结果两处维护。
- SPEC FR-MOCK-03 写作"内置 §16 的 5 个样例审批单"，但 §16 实为"未决事项"，5 个样例实际在 **§15**。按 §15 实现。
