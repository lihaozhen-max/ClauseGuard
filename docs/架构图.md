**关键约束（来自 SPEC）**

- `FR-SYS-01`：模拟审批系统**必须**是独立进程，工具服务只能通过 HTTP 访问它。
- `FR-SYS-02`：合同附件**禁止**对外暴露静态路由。
- `FR-SYS-03`：调用端所有请求**必须**带 `X-API-Key`。
- `LM-18`：`E2` 不可用（无 Key / 超时 / 报错）时，系统**必须**仍能跑通全部 AC01–AC19——LLM 是增强项，不是单点依赖。


**依赖方向铁律**

- 依赖**只能**自上而下：`api → tools → modules → {clients, llm, db, core}`。
- `logging/` 被所有模块依赖，它**禁止**反向依赖任何业务模块（避免循环）。
- `llm/` 暴露抽象接口，业务模块**只依赖抽象**——这样换端点（DeepSeek → 其他 OpenAI 兼容）不改业务代码。
- 任何模块**禁止**绕过 `db/` 直接用驱动建连接（工程规范 §8）。

## FIG-05 正常链路时序图

```mermaid
sequenceDiagram
    autonumber
    participant U as 调用端
    participant S as 工具服务
    participant A as 模拟审批系统
    participant F as 文件存储
    participant L as DeepSeek API
    participant D as MySQL

    U->>S: POST /api/tasks/pull
    S->>A: GET /approvals/pending
    A-->>S: 待办列表
    S->>D: upsert approval_tasks（按 instance_id 去重）
    S-->>U: created/updated 统计

    U->>S: POST /api/tasks/1/parse
    S->>A: GET 审批详情
    A-->>S: 表单 + 附件信息
    S->>A: GET 附件下载
    A-->>S: 文件流
    S->>F: 落盘 + SHA-256
    S->>S: 类型识别 → 文本提取 / OCR → 清洗
    S->>L: 关键字段兜底提取（仅在正则与条款定位都失败时）
    L-->>S: 字段值 + 原文片段
    S->>S: 证据子串校验
    S->>D: 写 contract_parses
    S-->>U: 解析结果

    U->>S: POST /api/tasks/1/review
    S->>D: 读 contract_parses + review_rules
    S->>S: 执行 R001…R011
    S->>L: R003/R004/R010 语义判定 + 摘要/关注点
    L-->>S: JSON 判定 + 摘要
    S->>S: 证据回验 + RL-AGG 汇总
    S->>L: 生成中文摘要与审批关注点
    S->>D: 写 rule_hits + review_results
    S-->>U: 风险结果

    U->>S: POST /api/tasks/1/write-comment
    S->>D: 读 review_results
    S->>A: POST 评论（带 idempotency_key）
    A-->>S: remark_id
    S->>D: 写 comment_logs + 更新 write_status
    S-->>U: 回写结果
```

**要点**

- LLM 只在**两处**出现：语义规则判定、摘要/关注点生成——图中已标注，其余全部确定性。
- 每次落库前都有一次**证据子串校验**（`PS-10`），校验失败即降级，不写脏证据。

## FIG-06 异常与重试时序图（blocked 链路）

```mermaid
sequenceDiagram
    autonumber
    participant U as 调用端/管理员
    participant S as 工具服务
    participant A as 模拟审批系统
    participant D as MySQL

    U->>S: POST /api/tasks/4/parse
    S->>A: GET 附件下载
    A-->>S: 404 附件不存在
    S->>D: task_status=blocked<br/>blocked_stage=parsing<br/>error_code=CONTRACT_ATTACHMENT_MISSING
    S->>D: task_logs(error)
    S-->>U: 409 + 错误码

    Note over U,D: 人工处理（补齐附件）后重试

    U->>S: POST /api/tasks/4/retry
    S->>D: retry_count+1<br/>清空 blocked_stage/error_code<br/>task_status=parsing
    S->>D: task_logs(retry)
    S->>A: 重新下载附件
    A-->>S: 文件流
    S->>S: 解析 → 审查 → 保存
    S->>D: task_status=done
    S-->>U: 成功

    Note over S,D: 另一条支路：评论回写失败
    S->>A: POST 评论
    A-->>S: 500
    S->>D: write_status=failed<br/>task_status 保持 done<br/>审查结果不删除
```

**两条关键规则**

- `ST-01-04` / `FR-COM-04`：**回写失败只改 `write_status`，任务保持 `done`，已产生的审查结果禁止删除**。图中的 Note 就是这个意思。
- `ST-01-02`：重试**必须**清空 `blocked_stage` 与 `error_code` 并把 `retry_count` 加 1。

## FIG-07 状态机

```mermaid
stateDiagram-v2
    [*] --> pending: 待办拉取创建
    pending --> parsing: 开始下载解析
    parsing --> reviewing: 解析成功
    reviewing --> done: 结果保存成功

    pending --> blocked: 审批接口异常
    parsing --> blocked: 附件缺失/下载失败/内容为空/OCR失败/解析失败
    reviewing --> blocked: 规则异常/接口异常

    blocked --> parsing: 人工重试（stage=parsing）
    blocked --> reviewing: 人工重试（stage=reviewing）

    done --> [*]
```

```mermaid
stateDiagram-v2
    [*] --> not_written: 任务创建
    not_written --> writing: 开始回写
    writing --> success: 审批系统返回成功
    writing --> failed: 回写失败
    failed --> writing: 管理员重新触发
    success --> [*]
```

**非法迁移（实现必须拒绝）**

- `done → pending`（`ST-01-03`：重复拉取禁止把已完成任务拉回）
- `blocked → done`（必须经 `parsing`/`reviewing`）
- `success → writing`（`ST-02-01`：重复回写返回既有结果并标 `duplicate=true`）

## FIG-09 解析流水线（PDF / Word / OCR 分流）

```mermaid
flowchart TD
    IN["合同附件"] --> DET["类型识别<br/>扩展名 + 文件头魔数<br/>PS-01"]
    DET -->|"docx"| W["python-docx<br/>段落即段单位"]
    DET -->|"pdf / 图片"| PDF["PyMuPDF 逐页取文本"]

    PDF --> JUDGE{"该页有效字符数<br/>低于 OCR_SCAN_PAGE_MIN_CHARS?<br/>PS-04"}
    JUDGE -->|"否：文本页"| TXT["文本提取"]
    JUDGE -->|"是：扫描页"| OCR["PaddleOCR<br/>文本 + 文本框坐标"]
    DET -->|"图片"| OCR

    W --> CLEAN["文本清洗<br/>去页眉页脚/连续空白<br/>PS-02"]
    TXT --> CLEAN
    OCR --> CLEAN
    CLEAN --> PMAP["页码映射<br/>page_map_json<br/>PS-03"]
    PMAP --> EXTRACT["字段提取（三层递进）<br/>PS-06"]

    EXTRACT --> L1["第 1 层：正则 / 模板"]
    L1 --> L2["第 2 层：条款标题定位"]
    L2 --> L3["第 3 层：LLM 兜底<br/>仅 5 个关键字段<br/>PS-07"]
    L3 --> VERIFY["证据子串校验<br/>PS-08 / PS-10"]
    VERIFY --> FR["FieldRecord ×16<br/>值+原文+位置+状态"]
    FR --> POS["position 生成<br/>text 或 ocr 两种格式"]
    POS --> OUT[("contract_parses")]
```

**分流规则**

- 混合文档（部分页扫描）→ `parse_mode` **必须**取 `ocr`（`PS-05`，从严），保证 `position` 格式唯一。
- LLM 兜底**只**作用于 `contract_amount`、`party_a`、`party_b`、`effective_date`、`expiry_date` 五个关键字段（`PS-07`）。
- 任何字段失败**不得**中断整体解析（`FR-PARSE-10`）。

## FIG-10 规则引擎结构（11 规则 × 5 模式 + 汇总）

```mermaid
flowchart TD
    LOAD["规则加载<br/>review_rules 中 rule_status=enabled<br/>FR-RULE-01"] --> DISPATCH{"按 match_mode 分派<br/>FR-RULE-02"}

    DISPATCH -->|"regex"| MR["正则匹配器<br/>RL-005"]
    DISPATCH -->|"keyword"| MK["关键词匹配器<br/>RL-003 / RL-009"]
    DISPATCH -->|"threshold"| MT["阈值比较器<br/>RL-001 / RL-002<br/>严格大于才命中"]
    DISPATCH -->|"presence"| MP["存在性检查器<br/>RL-006 / RL-007 / RL-008"]
    DISPATCH -->|"llm_semantic"| ML["语义判定器<br/>RL-003 / RL-004 / RL-010"]

    MR --> EV["证据截取<br/>取合同原文句子"]
    MK --> EV
    MT --> EV
    MP --> EV
    ML --> EV

    EV --> GUARD{"证据是 full_text<br/>连续子串？<br/>PS-10"}
    GUARD -->|"是"| HIT["hit"]
    GUARD -->|"否：规则命中"| BUG["报警：规则实现有缺陷"]
    GUARD -->|"否：LLM 命中"| UNC["降级为 uncertain"]

    HIT --> SNAP["快照 risk_level + suggestion<br/>FR-RULE-09"]
    UNC --> SNAP
    SNAP --> SAVE[("rule_hits<br/>(task_id, rule_id) 唯一")]

    SAVE --> AGG{"RL-AGG 汇总<br/>只统计 hit_status=hit"}
    AGG -->|"存在 high"| RH["overall = high"]
    AGG -->|"否则存在 medium"| RM["overall = medium"]
    AGG -->|"其余（含空集 / 全 uncertain）"| RL["overall = low"]
```

**11 条规则的模式分布**

| 模式 | 规则 | 条数 |
|---|---|---|
| `threshold` | R001 预付款比例、R002 付款周期 | 2 |
| `presence` | R006 主体缺失、R007 金额缺失、R008 保密缺失 | 3 |
| `regex` | R005 管辖地 | 1 |
| `keyword` | R003 自动续约、R009 数据处理 | 2 |
| `presence + llm_semantic` | R004 违约责任、R010 知识产权 | 2 |
| `presence + keyword` | R011 验收标准缺失 | 1 |
| **合计** | | **11** |

> **只有 3 条规则会用到 LLM**（R003/R004/R010），其余 8 条完全确定——这正是"规则为主、LLM 兜底"的落点。

## FIG-11 幂等与唯一索引分布（4 道防线）

```mermaid
flowchart LR
    subgraph F1["防线 1 · 任务去重"]
        A1["approval_tasks<br/>UNIQUE(instance_id)"]
    end
    subgraph F2["防线 2 · 附件不重复"]
        A2["approval_attachments<br/>UNIQUE(task_id, attachment_code)"]
    end
    subgraph F3["防线 3 · 结果与命中不重复"]
        A3["review_results<br/>UNIQUE(task_id)"]
        A4["rule_hits<br/>UNIQUE(task_id, rule_id)"]
        A5["contract_parses<br/>UNIQUE(task_id, attachment_id)"]
    end
    subgraph F4["防线 4 · 评论不重复"]
        A6["comment_logs<br/>UNIQUE(idempotency_key)"]
    end
    F1 --> F2 --> F3 --> F4
```

**为什么必须靠数据库约束**（`FR-APP-03`）

应用层"先查后插"在并发下会失效：两个请求同时查到"不存在"，然后都插入。唯一索引是唯一可靠的防线——**重复拉取、重复解析、重复审查、重复回写**四种场景全部由索引兜底，应用层只负责捕获冲突并转为 upsert。

| 场景 | 防线 | SPEC |
|---|---|---|
| 重复拉取同一审批单 | `UNIQUE(instance_id)` | `FR-APP-02/03` |
| 重复下载同一附件 | `UNIQUE(task_id, attachment_code)` | `FR-ATT-06` |
| 重复解析同一附件 | `UNIQUE(task_id, attachment_id)` | `FR-PARSE-09` |
| 重复执行审查 | `UNIQUE(task_id, rule_id)` | `FR-RULE-07` |
| 重复保存结果 | `UNIQUE(task_id)` | `FR-REV-05` |
| 重复回写评论 | `UNIQUE(idempotency_key)` | `FR-COM-02` |

```mermaid
flowchart LR
    M0["M0 环境与骨架<br/>DO1-DO6"] --> M1["M1 模拟审批+拉取去重<br/>AC01-AC02"]
    M1 --> M2["M2 下载+解析+提取<br/>AC03-AC07"]
    M2 --> M3["M3 规则引擎+LLM<br/>AC08-AC10"]
    M3 --> M4["M4 汇总+保存+回写<br/>AC11-AC15"]
    M4 --> M5["M5 异常阻塞+重试+日志<br/>AC16-AC18"]
    M5 --> M6["M6 前端五模块"]
    M6 --> M7["M7 闭环演示+交付<br/>AC19"]
    M5 --> M7

    M2 -.->|"重依赖：paddlepaddle/paddleocr 安装耗时"| R1["风险：安装时间长"]
```

**依赖说明**

- `M2` 是**最长的一步**：要装 paddlepaddle + paddleocr（体积大），还要调优扫描页判定阈值与字段词表。
- `M6` 前端**只依赖 `M5` 的接口**，因此在后端接口稳定后可以与 `M5` 部分并行。
- `OPEN-01`（`asyncmy` vs 同步 `pymysql`）**必须在 M0 定**，否则 `M1` 的 ORM 代码要返工。
