## 1. 项目范围与目标

### 1.1 一句话定义

在企业合同审批流程中充当"法务审查机器人"：自动拉取待审批合同 → 下载附件 → 解析（含 OCR）→ 提取字段与条款 → 执行风险规则 → 汇总生成带原文证据的风险意见 → 保存结果 → 将中文评论写回审批系统评论区。

**只提供风险识别、解释与审批关注点，不替代人工作出审批决定。** `[PRD 3][PRD 4.1]`

### 1.2 业务闭环（9 步，不可裁剪）`[PRD 6]`

```
① 拉取待审批合同 → ② 读取审批详情 → ③ 下载合同附件 → ④ 解析合同（文本/OCR）
→ ⑤ 提取合同字段 + 条款识别 → ⑥ 执行风险审查 → ⑦ 形成整体风险结果
→ ⑧ 保存审查结果入库 → ⑨ 写回审批系统评论区 → 人工最终审批
```

### 1.3 MVP 范围（15 项）`[PRD 20]`

模拟审批系统、待办拉取、任务去重、PDF/Word/图片读取、OCR、字段提取、11 类规则、风险等级计算、证据定位、结果保存、评论生成、评论回写、`blocked` 异常状态、人工重试、全链路日志。

**不建设**复杂企业审批工作流。

### 1.4 交付物结构 `[PRD 23]`

```
ClauseGuard/                        ← 本项目根目录（提交时可改名为「组名_姓名_合同审查_行业」）
├── backend/                        工具服务（FastAPI）
├── frontend-or-client/             调用端（Vue 3 + Element Plus）
├── mock-approval-system/           [补充] 模拟审批系统（独立服务）
├── database/                       初始化脚本 + 规则种子数据
├── sample_contracts/               示例合同（含扫描件）
├── docs/                           本设计文档 + 接口说明 + 演示说明
├── tests/                          测试

├── README.md

```

> `[补充]` PRD 未单列模拟审批系统目录，但 MVP 第 1 项要求"模拟审批系统"，且它是完整闭环演示的前置条件，故独立成模块。

### 3.2 模块职责（对应 `[PRD 16]`）

| 模块 | 职责 | 关键产出 |
|---|---|---|
| Approval Module | 待办获取、审批详情获取、**按唯一业务标识去重** | `approval_tasks` 记录 |
| Attachment Module | 附件下载、文件落盘、文件信息与校验 | `approval_attachments` |
| Parser Module | PDF/Word 解析、OCR、字段提取、条款识别 | `contract_parses`（四元组结构） |
| Rule Engine | 规则加载、匹配执行、命中保存、风险等级汇总 | `rule_hits` |
| Review Module | 风险汇总、中文摘要、审批关注点、评论文本生成 | `review_results` |
| Comment Module | 调用审批接口、回写评论、保存日志、失败重试 | `comment_logs` |
| Logging Module | 全链路日志与错误信息 | `task_logs` |

### 3.3 部署形态

- **工具服务**：单进程 FastAPI（uvicorn），非异步阻塞操作（PDF 解析、OCR）放线程池/`run_in_executor`，避免阻塞事件循环。
- **模拟审批系统**：独立进程（独立 FastAPI 应用 + 自带数据），通过 HTTP 被工具服务调用——**保持"外部系统"边界**，便于日后替换为真实审批系统。
- **MySQL**：Docker Compose 单实例，含初始化 SQL（建表 + 规则种子数据）。
- **前端**：Vite 构建，开发期独立端口、生产期产物由后端静态托管。

### 4.3 关键约束

- `approval_tasks.instance_id` 唯一索引 —— **去重唯一性的最终保障**（并发下以数据库约束为准，不能只靠应用层查重）。
- `review_results.task_id` 唯一索引 —— 一任务一结果，重复执行做 upsert 而非插入。
- `comment_logs.idempotency_key` 唯一索引 —— 回写幂等。
- 所有外键 `ON DELETE RESTRICT`（审查结果与日志不允许被级联删除，符合"不得删除已产生结果"）。

## 5. 状态机

### 5.1 任务状态 `[PRD 11]`

```
                 ┌─────────┐
   拉取入库 ────► │ pending │
                 └────┬────┘
                      ▼
                 ┌─────────┐   附件缺失/下载失败/解析失败/内容为空/OCR失败
                 │ parsing │ ─────────────────────────────┐
                 └────┬────┘                              │
                      ▼                                   ▼
                 ┌───────────┐  规则执行异常/接口异常 ┌─────────┐
                 │ reviewing │ ─────────────────────► │ blocked │
                 └─────┬─────┘                        └────┬────┘
                       ▼                                   │ 人工重试
                  ┌──────┐                                 │
                  │ done │ ◄───────────────────────────────┘
                  └──────┘        （重试回到 blocked_stage 标记的阶段）
```

- `done` 的判定：审查结果已入库。**评论回写失败不回退任务状态**，只改 `write_status`（`[PRD 13]`：不得删除已产生的审查结果）。
- `blocked` 必须记录 `blocked_stage` + `error_code`，重试从此阶段重新进入。`[PRD 11]`

### 5.2 回写状态 `[PRD 12]`

```
not_written ──► writing ──► success
                   │
                   └──────► failed ──（管理员重新触发）──► writing
```

## 7. 规则引擎设计

### 7.1 规则数据模型

一条规则 = `rule_code` + `rule_name` + `risk_level` + `rule_status` + `match_mode` + `match_text` + `match_params_json` + `suggestion_text` + `target_section`。`[PRD 7.6]` + `[补充]`

### 7.2 `match_mode` 枚举 `[补充]`

| 模式 | 语义 | 证据来源 |
|---|---|---|
| `regex` | 正则匹配全文/限定部位 | 正则捕获组命中的原文片段 |
| `keyword` | 关键词集合命中 | 命中关键词所在句子 |
| `threshold` | 数值/比例与 `match_params_json` 阈值比较 | 提取出的字段值 + 其原文 |
| `presence` | 必需条款/字段是否存在（反向规则） | 缺失说明 + 最接近的原文上下文 |
| `llm_semantic` | 语义判断（仅 R003/R004/R010） | **LLM 必须回填合同原文片段与页码**，模型不得自造证据 |

### 7.3 11 条规则的实现路线 `[PRD 7.7]`

| 规则 | 名称 | 模式 | 实现要点 | 风险等级 |
|---|---|---|---|---|
| R001 | 预付款比例风险 | `threshold` | 提取预付款比例，与 `{"max_ratio":0.30}` 比较 | high |
| R002 | 付款周期风险 | `threshold` | 提取付款天数/账期，超阈值判定 | medium |
| R003 | 自动续约风险 | `llm_semantic` + `keyword` 兜底 | 关键词（自动续约/自动顺延/期满自动）→ 命中即证据；LLM 判语义变体 | medium |
| R004 | 违约责任风险 | `llm_semantic` + `regex` 兜底 | 先查违约条款是否存在（缺失即命中）；存在则由 LLM 判"明显不对等" | high |
| R005 | 管辖地风险 | `regex` | 匹配管辖/仲裁表述，判断是否为对方所在地/不利管辖地 | medium |
| R006 | 主体信息缺失 | `presence` | 校验签约主体、对方名称是否齐备 | high |
| R007 | 合同金额缺失 | `presence` | 校验金额与币种是否齐备 | high |
| R008 | 保密条款缺失 | `presence` | 是否存在保密条款 | medium |
| R009 | 数据处理风险 | `keyword` + `llm_semantic` | 是否涉及数据采集/共享/处理/存储，及是否约定合规义务 | medium |
| R010 | 知识产权风险 | `llm_semantic` + `presence` | 归属条款缺失即命中；存在则由 LLM 判是否明确 | high |
| R011 | 验收标准缺失 | `presence` + `keyword` | 是否存在验收时间/方式/标准 | high |

> **设计原则**：能确定性判定的绝不用 LLM。LLM 只在"语义判断"和"摘要生成"两处出现，且**证据必须来自合同原文**——由系统回填，不接受模型生成的证据文本。

### 7.4 风险汇总 `[PRD 8]`

```
存在任意 high   → 整体 = high
否则存在 medium → 整体 = medium
否则            → 整体 = low
```

### 7.5 审查结果结构 `[PRD 9]`

```json
{
  "overall_risk_level": "high",
  "summary_text": "合同存在较高预付款比例及验收标准缺失问题",
  "focus_points": ["确认80%预付款是否符合公司付款政策", "补充明确的交付验收标准"],
  "rule_hits": [
    {
      "rule_name": "预付款比例风险",
      "risk_level": "high",
      "evidence_text": "合同签订后三日内支付合同总额80%",
      "evidence_position": "第4页付款条款",
      "suggestion": "建议降低预付款比例或增加履约保障措施"
    }
  ]
}
```

## 8. 文档解析与证据定位

### 8.1 支持格式与库选型

| 格式 | 主力 | 兜底 | 说明 |
|---|---|---|---|
| PDF（文本型） | PyMuPDF | pdfplumber | PyMuPDF 快且带页码；pdfplumber 用于表格与精细坐标 |
| PDF（扫描型） | 逐页转图 → PaddleOCR | — | 判定：单页可提取字符数低于阈值即视为扫描页 |
| Word | python-docx | — | 段落即天然"段"单位 |
| 图片 | PaddleOCR | — | |

### 8.2 `position` 规范 `[补充]`

PRD 只给了示例 `"第2页 第3段"`。统一规则：

| 解析模式 | 格式 | 示例 |
|---|---|---|
| 文本型 | `第{页}页 第{段}段` | `第2页 第3段` |
| OCR 型 | `第{页}页 区域({x},{y})` | `第1页 区域(120,480)` |

前端按 `parse_mode` 决定展示形式；两种都保证**能在原文里定位**。

### 8.3 字段四元组 `[PRD 7.5]`

```json
{
  "field_name": "contract_amount",
  "field_value": "500000",
  "source_text": "本合同总金额为人民币伍拾万元整",
  "position": "第2页 第3段",
  "extract_status": "success"
}
```

`extract_status` ∈ `success` / `missing` / `failed`。**每个字段都必须有四元组**，`[PRD 4.3]`。

### 8.4 字段与条款清单 `[PRD 6][PRD 1.3.5]`

- **基本信息**：合同标题、合同编号、签约主体、对方名称、合同金额、币种、生效时间、到期时间
- **条款**：付款、交付、验收、违约、保密、数据、知识产权、争议解决

### 8.5 提取策略 `[补充]`

三层递进，每层都必须产出四元组：
1. **模板/正则**：金额、日期、编号等强格式字段（高准确、可解释）。
2. **条款定位**：按标题词（"付款方式""验收"…）切分条款段落，得到条款原文与位置。
3. **LLM 兜底**：仅当 1/2 均为 `missing` 且字段属于关键字段（金额、主体、期限）时调用，**要求返回原文片段与页码，系统校验该片段确实存在于 `full_text` 中**，校验不过则标记 `failed`。

## 9. LLM 集成设计

### 9.1 用途边界（严格）

| 允许 | 禁止 |
|---|---|
| R003/R004/R010 的语义判断 | 生成风险证据原文（必须来自合同） |
| `summary_text` 中文摘要生成 | 决定最终风险等级（由 §7.4 算法决定） |
| `focus_points` 审批关注点生成 | 替代人工审批结论 |

### 9.2 接入方式

- 端点：**DeepSeek 官方 API**，`base_url=https://api.deepseek.com`（OpenAI 兼容），客户端用 `openai` SDK。
- 配置全部经 `pydantic-settings` 从 `.env` 读取：`LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`、`LLM_TIMEOUT_SECONDS`、`LLM_MAX_TOKENS`、`LLM_TEMPERATURE`、`LLM_ENABLED`。
- **Key 绝不进代码库**，`.env.example` 只留占位符（`[PRD 19.5]`、工程规范 §7）。
- 结构化输出：要求返回 JSON（`rule_code` / `hit` / `evidence_text` / `position` / `reason`），系统做 schema 校验 + 证据回验。

### 9.2.1 实测结果（2026-09-17，已用真实 API 验证）

`GET /v1/models` 实际返回的模型只有两个，**没有 `deepseek-chat`**（该名会被接受但不在列表中，不采用）：

| 模型 | 延迟 | tokens | `reasoning_content` | 返回 JSON | 结论 |
|---|---|---|---|---|---|
| `deepseek-flash` | 1.30s | 248 | 有（200 字符） | ✅ 合法 JSON | **默认选用**：快、便宜、已具备推理能力 |
| `deepseek-v4-pro` | 3.56s | 302 | 有（213 字符） | ✅ 合法 JSON | 质量优先时切换（改 `.env` 一行） |

验证用例（R004 违约责任不对等）返回 `{"hit": true, "risk_level": "high", "reason": "..."}`，**判定正确且 JSON 可直接解析，无需剥离 Markdown 代码块**——语义型规则路线成立。

### 9.2.2 推理模型的两个硬性约束 `[重要]`

1. **`max_tokens` 必须留足**：推理 token 计入 `max_tokens`。实测 `max_tokens=8` 时 `content` 返回**空字符串**（推理过程吃光了配额），而 HTTP 状态仍是 200 —— 属于**静默失败**，必须显式防御。默认取 `LLM_MAX_TOKENS=1024`。
2. **`reasoning_content` 的处理**：这两个模型在 `message` 里额外返回 `reasoning_content`（与 `content` 平级）。
   - **只解析 `content`**，`reasoning_content` 仅可用于日志/调试；
   - **多轮对话时绝不把 `reasoning_content` 回传给模型**；
   - 解析失败（如 `content` 为空）应视为该次 LLM 调用失败 → 走 §9.3 降级，而非把空结果当"未命中风险"。

> 这两条已同步写入 `.env.example` 注释，实现时必须遵守。


### 9.3 降级策略 `[补充]`

| 情况 | 行为 |
|---|---|
| `LLM_ENABLED=false` 或 Key 缺失 | 语义型规则退化为关键词/条款存在性判定，`hit_source=rule`；摘要用模板拼接 |
| LLM 超时 / 报错 / 返回非法 JSON | 单条规则记 `uncertain`（不阻塞任务），摘要走模板；**任务不进入 `blocked`** |
| 证据回验失败 | 丢弃该 LLM 命中，记日志 |

> 降级设计的意义：**保证无网络/无 Key 也能完成 AC01–AC19 全闭环演示**，LLM 只是增强项。

### 9.4 可插拔

`LLMClient` 抽象接口 + `DeepSeekClient` 实现 + `NullLLMClient`（降级），业务层只依赖抽象——便于日后换其他 OpenAI 兼容端点。
