## 3. 关键发现与实现决策

### 3.1 【R-01】AC19 用例当场抓出一个真实缺陷：审批表单数据从未落库

写端到端用例时断言"详情页应有表单数据"，结果是空的。追下去发现：

- `approval_tasks.contract_type` 与 `form_data_json` 这两列**在 M1–M6 期间从未被写入过**
  （`grep` 全仓只有定义与读取，没有任何 `INSERT/UPDATE`）；
- 根因是 SPEC/设计把"第 ② 步 详情"的实现理解成了"顺便取一下附件"：
  `ensure_attachments` 确实会调 IF-02，但拿到的 `contract_type` / `form_data` 被直接丢弃；
- 后果是 **FR-UI-02 的"表单数据"永远为空**，详情页的合同类型也一直是兜底值。

**修法**（最小且贴合设计原意）：设计 §7 对 `form_data_json` 的注解是
"审批表单字段（**PRD §6 第二步要求读取**）"，所以第 ② 步本来就该把详情落库。于是：

1. 新增 `cache_approval_snapshot()`：把 `contract_type` / `form_data` 写进任务行；
2. `parse_task`（承载第 ②③④⑤ 步）开头调用 `sync_approval_snapshot()`，
   **尽力而为**——审批系统不可达时只记 `warning`，不改变任务状态（与 LM-14"LLM 失败不阻塞"同一思路）；
3. 前端详情页对**尚未解析**的任务改从 IF-02（`/api/approvals/{id}`）取表单，
   该 REST 形态在 M1 就是"为了调用端详情页"而加的。

回归用例：`test_if12_form_data_is_cached_after_parse`、`test_approval_snapshot_is_best_effort`、
`test_task_row_matches_final_api_view`（视图=库）。

### 3.2 【R-02】两条 M5 用例依赖"别的用例留下的库状态"

把 `-k` 单独挑出来跑时，`test_m5_logs.py` 里有两条失败——**不是实现缺陷**：
它们默认"前面的用例已经解析过 AP-002 / 已给 AP-001 回过写"。全量跑时靠执行顺序侥幸通过，
单独跑就暴露了。已改为调用 `_run_loop()` 自行把链路推到目标阶段（每步都幂等），
用例之间不再有顺序依赖。

这与 M5-R-01 是同一类问题的两个层次：那次修的是"**跨轮**污染"（会话级清库），
这次修的是"**同轮内**用例间耦合"。

### 3.3 【R-03】闭环用例用 `NullLLMClient`，保证结论可复现

AC19 验证的是**闭环本身**，不是"某个 LLM 输出下的表现"。用例通过依赖覆盖把 LLM 换成
`NullLLMClient`，语义规则走降级路径，11 条规则的判定与整体等级完全确定。
真实 LLM 的通路由标 `llm` 的用例和 `demo_closed_loop.py`（默认走真实 Key）覆盖。

`expected_results.json` 的 AP-001 期望结果本身就是按"LLM 关闭时 R004/R009 为 `uncertain`、
仍是 `high`"校准的，两种模式都能跑通。

### 3.4 【R-04】演示脚本临时"补交附件"，跑完自动还原

AC17 要求"补齐附件后重试"。真实演示时，脚本把 `AP-002_服务合同.pdf` 复制成 AP-004 声明的
文件名（模拟审批人补交合同），重试完成后**自动删除**，恢复 AC16 的"附件缺失"基线——
否则样例集会被永久改坏，AC16 再也演示不出来。

### 3.5 【R-05】交互态截图：同源 iframe 夹具，用完即删

headless Chrome 的 `--screenshot` 只能截"加载完成时"的画面，点不出对话框。
为了给 FR-UI-08 留下一张"新增规则对话框"的真实截图，用一个临时同源 iframe 夹具
（`public/__shot.html`）载入调用端、轮询等按钮出现后 `click()`，再把整个 iframe 截下来。
夹具在截图后**立即删除**，不进交付物（否则会被打进 `dist/`）。

**本轮又发现并修复了两个真实竞态**——这是"补测"最该产生的价值。

### 7.1 【R-09】并发写冲突：两处"先查再插"在并发下变成 500

全项目 7 张业务表里，有 5 张的唯一键写入走的是 `INSERT ... ON DUPLICATE KEY UPDATE`
（`approval_tasks` / `approval_attachments` / `contract_parses` / `review_results` / `rule_hits`）。
**只有两处是"先查再插"**，它们正是本轮被抓出来的：

| 场景（6 路真并发） | 修复前 | 修复后 |
|---|---|---|
| 并发回写同一条评论 | `IntegrityError 1062 … uk_comment_logs_idempotency_key` → **HTTP 500** | 库里 1 行、审批系统侧 1 条、`remark_id` 一致，落败者返回 `duplicate=true` |
| 并发新增同一 `rule_code` | `IntegrityError 1062 … uk_review_rules_rule_code` → **HTTP 500** | 1 次成功 + 5 次 `422 VALIDATION_ERROR` |

修法不是"加把锁"，而是把注释里那句"**唯一索引是最终保障**"真正落到代码上：

- `modules/comment/service.py`：改为 `INSERT ... ON DUPLICATE KEY UPDATE` 原子确保"一行逻辑评论"存在，
  再用**加锁读**（`with_for_update`）取权威状态。
  *为什么必须加锁读*：REPEATABLE READ 下普通读会命中事务开始时的快照，看不到并发事务刚提交的
  `success`——M1 在拉取路径上踩过同一个坑（见 `modules/approval/service.py` 的注释）。
  拿到锁后若发现已是 `success`，直接按 FR-COM-06 返回既有结果，**不会重复请求审批系统**；
- `modules/rules/admin.py`：预检查保留（它负责给出可读的冲突信息），
  但把 1062 唯一键冲突翻译成 `422 VALIDATION_ERROR`，让唯一索引兜住并发窗口。

### 7.2 并发不变量（`tests/test_m7_concurrency.py`，6 例）

每个"调用方"都开自己的 session、用 `asyncio.gather` 真并发，验证的是收敛性而非单线程正确性：

| 场景 | 断言的不变量 |
|---|---|
| 6 路并发回写同一评论 | 1 行评论、远端 1 条、`remark_id` 一致、且**至少一个调用走 `duplicate` 分支**（若断言不到就说明并发窗口没重叠，用例失去意义） |
| 6 路并发回写（收敛） | 终态 `write_status=success`，`comment_logs` 恰好 1 行 |
| 6 路并发建同一 `rule_code` | 成功 1 次，其余 422，**无 `IntegrityError`** |
| 并发改同一规则的**不同字段** | 两边改动都留下（不丢更新） |
| 6 路并发拉全量待办 | 每个 `instance_id` 恰好 1 条任务，无 1213 死锁 |
| 4 路并发审查同一任务 | `review_results` 1 行；`rule_hits` 行数 == 去重规则数 == 启用规则数 |

> 这里也踩到一次**用例自身的顺序耦合**：`comment_ready_task` 夹具只清了库里的
> `comment_logs`，却没清模拟审批系统**内存里**同一个幂等键的评论（`test_m4_review_db`
> 的 REST 闭环早已写过一次，`review_id` 复用后幂等键相同），于是"本次只新增 1 条"在
> 第一次全量跑时失败。夹具已改为**两处状态一起清**。教训与 §3.2 同类：一次全量跑永远比十次单跑更能暴露问题。

设计要点：

- **只读**：不改配置、不建表、不写库；失败项直接给出可复制的修复命令；

  （只看"端口被占用"会把别人的项目当成自己的，见 `docs/错题本.md` D-4）；
- 用项目已有的 `pymysql` 检查真实表结构与规则种子，不引入任何新依赖（调用端身份用标准库 `urllib`）。

## 7.8 前端渲染基线（`scripts/bench_ui.py`）

`bench.py` 量接口，这个量**页面**：真实 Chrome + 真实后端，造数后测"导航 → 目标行数出现在 DOM"的墙钟时间：

| 场景 | 数据量 | 耗时 | DOM 节点 | JS 堆 |
|---|---|---|---|---|
| 待办列表 | 5 条任务 | 510ms | 349 | 15.0 MB |
| 待办列表 | **1005 条任务** | **406ms** | 723 | 16.6 MB |

## 7.9 窄屏适配（<1100px 断点）

原来只按 1760px 的桌面宽度设计，窗口拖窄或投影仪上（1024×768）会横向溢出。现在：

- 侧栏折叠成 64px 图标条（`el-menu` 的 `collapse`），顶栏副标题与按钮文字同步收起；
- 详情页的 `el-descriptions` 从 3 列降到 1 列、表单区从 2 列降到 1 列；
- 规则命中页的统计块从竖排改成横排，不跟风险徽标抢宽度；
- 定宽表格列靠 `el-table` 自带的横向滚动兜住，外层卡片不再被撑破。

实现方式值得记一笔：**用响应式布尔值驱动属性，而不是纯 CSS 媒体查询**——
`el-aside` / `el-descriptions` 的宽度与列数是**属性**、会写成行内样式，媒体查询压不过它。
`src/composables/useViewport.ts` 的初值直接取 `window.innerWidth`，因此首帧就是对的，窄屏下不会先闪一下宽布局。

验证：`tests/test_m7_ui_e2e.py::test_narrow_viewport_has_no_horizontal_overflow` 用
`Emulation.setDeviceMetricsOverride` 切到 **1024×768 与 800×900** 两档，
逐个页面断言"文档不横向溢出 / 侧栏已折叠 / 表格没有超出版口"。
新增截图 `窄屏1024_待办列表.png`、`窄屏1024_规则命中.png`、`窄屏800_任务日志.png`；
**1760px 的既有观感未变**（断点只作用于 <1100px），M6/M7 的既有截图继续有效。

### 7.10 浏览器支持范围（**声明，而不是逐引擎验证**）

> 结论先说：本项目**只声明支持 Chromium 系浏览器**（Chrome / Edge 等，2023 年后的版本）。
> 不把"Firefox / Safari 兼容性验证"列为待办——它**不属于本项目的范围**。

理由：

1. **规范没有这条要求**。PRD / SPEC / 设计全文都没有浏览器兼容性条款；与界面相关的只有
   FR-UI-01…08 与 NF-10（风险等级三色区分）。凭空补一条规范外的验证项，只会制造假的工作量。
2. **调用端是内网单组织工具**（设计 §8 的定位）。使用者是同一家公司的审批人，
   这种场景的通行做法就是**声明支持范围**，而不是维护浏览器矩阵——那是组织策略，不是技术债。
3. **在 Windows 上"真跨引擎"本来也做不完整**：Chrome 与 Edge 同为 Blink（等于只测一个引擎）；
   Playwright 在 Windows 上提供的 WebKit 构建**不是真 Safari**，测了也不能代表 Safari。
   要真做，得有 macOS 机器 + 真 Safari，成本远超收益。
4. **它要防的风险在这里几乎不存在**：界面是 Element Plus 组件（跨浏览器支持由上游维护）
   + 普通 CSS + `fetch`/`vue-router`，没有引擎专有 API。唯一 Chrome 专有的是
   `bench_ui.py` 里的 `performance.memory`，已做空值兜底，而且那只是开发期脚本。

**什么时候才需要它**：对外发布、或客户环境确实存在 Firefox / Safari 用户。
那时的正确做法是把它当成**产品范围决策**——先在 SPEC 里写兼容性要求，
再在 CI 里加 Playwright 的 `firefox` / `webkit` projects，而不是事后补一次浏览器巡检。

**已做的**：`tests/test_m7_ui_e2e.py` 在 Chrome 上真实点击验证（7 例）；
`_cdp_client.CHROME_CANDIDATES` 同时收录了 Edge，换引擎只需调整候选顺序——
留好了口子，但现在不去填它。

### 7.12 "端口 ≠ 身份"：一处会让人误判的探活缺陷

**触发场景**：交付自检时本机同时开着另一个项目（InsightTrace）的 Vite dev server，它占着 5173，
并把自己的 `/api` 代理到自己的后端。本项目的前端因此落到 **5174**。

**现象**：全量回归跑出 **295 passed, 7 errors**，7 条 `ui` 用例全部在
`wait_for_text('待办任务')` 处失败——**报错信息指向本项目的代码**，但真实原因是
浏览器打开的是**别人的前端**（页面里根本没有本项目的列表）。

**根因**：`tests/test_m7_ui_e2e.py` 把 `WEB_URL` 写死为 `127.0.0.1:5173`，而 `_web_ready()`
的判据只有"HTTP 200"。端口是本机共享资源，"200"完全不构成身份证据 ——
同一个错误在 `scripts/dev_up.ps1` 里也犯过一次（它因此报"前端已在运行"，而我们的前端从未启动）。

**修法**（三处统一口径）：

| 位置 | 修改 |
|---|---|
| `tests/test_m7_ui_e2e.py` | `WEB_URL` 不再写死：按**页面含 `ClauseGuard`** 在 5173–5180 顺序定位，支持 `CLAUSEGUARD_WEB_URL` 覆盖；`_web_ready()` 增加身份复核 |
| `scripts/dev_up.ps1` | 前端探活加身份校验；被占用则顺延 5174…5180 并打印真实地址 |
| `scripts/dev_status.ps1` | 前端 `Expect = 'ClauseGuard'`（占用者非本项目时显示"端口被占用（非本服务）"），并列出本项目调用端 |
| `scripts/preflight.py` | 新增「本项目调用端身份」检查项（标准库 `urllib`，不引入新依赖） |

**验证**：

```
$ uv run pytest -q -m ui        # 修复后
7 passed, 295 deselected, 1 warning in 32.42s
$ uv run pytest -q              # 修复后全量
302 passed, 2 warnings in 205.85s (0:03:25)
   [OK] 本项目调用端身份    http://127.0.0.1:5174（按页面身份确认）      # preflight，退出码 0
```
