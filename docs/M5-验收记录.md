## 3. 关键发现与实现决策

### 3.1 【R-01】测试套件受"上一轮运行的库状态"污染（已从根上修掉）

M5 的第一轮回归出现 8 个失败，**没有一个是实现缺陷**，全部来自同一个根因：
测试会真实写库，而上一轮（含我手工跑的冒烟）留下的状态让本轮的**前提**不成立，例如

- 上一轮把 AP-004 重试成了 `done` → 本轮"附件缺失应 blocked"永远不成立
  （任务在终态时按 ST-01-03 不回退，这是**正确行为**，错的是测试前提）；
- 上一轮已把 AP-004 的附件下载到本地并登记 → 本轮 `ensure_attachments` 直接复用，不再重新下载。

零散打补丁（逐个用例改前提）能过，但每加一个里程碑就会再炸一次。因此改为在
`tests/conftest.py` 加**会话级 autouse 基线重置**：整个测试会话开始前清空
`comment_logs / review_results / rule_hits / contract_parses / approval_attachments / task_logs / approval_tasks`
与附件落盘目录（MySQL 未就绪时自动跳过）。

> 代价是每次跑测试会清掉开发库的业务数据——但 `POST /api/tasks/pull` 随时可重建，
> 且 `.env` 指向的本就是开发库；相比"排查跨轮污染"，这个代价明显更划算。
> 需要保留现场做演示时，用 `pytest -k <单个用例>` 或先备份即可。

### 3.2 【R-02】FR-RULE-06 与 FR-RULE-11 的边界

两条要求容易混淆，实现上必须分清：

| 情形 | 规范 | 实现位置 |
|---|---|---|
| **单条规则**自身抛异常 | 该规则记 `uncertain`，**禁止**中断其他规则（FR-RULE-06） | `_evaluate_rule` 的 per-rule try/except |
| **规则执行阶段**异常（加载规则、重建文档、写命中失败…） | 任务 `blocked` / `reviewing` + `RULE_EXECUTION_FAILED`（FR-RULE-11） | `run_rules_for_task` 的阶段级 try/except（`AppError` 直接透传，不吞业务错误） |

### 3.3 【R-03】重试语义按 FIG-06：**从断点续跑并跑完**

设计 §14 只说"人工重试"，容易实现成"回到断点阶段就结束"。但架构图 FIG-06 的重试时序明确是：

```
POST /retry → retry_count+1、清断点、task_status=parsing → 重新下载 → 解析 → 审查 → 保存 → done
```

因此 `retry_task` 实现为：**校验并进入断点阶段 → 继续调用既有工具跑完剩余流程**
（复用经过验证的 `parse_task` / `run_full_review`，而不是另写一套），
管理员点一次重试，任务跑到终态；中途再次失败则重新 `blocked` 并照常抛错。

### 3.4 【R-04】`ensure_attachments` 的短路行为影响"重试是否重新下载"

`ensure_attachments` 在库中**已有附件记录**时直接复用、不重新下载（M2 的设计，避免重复下载）。
因此"修好审批系统后重试"能重新下载的前提是：该任务此前**没有**成功下载过。
实现与测试都按此口径；`docs/接口说明.md` 已注明。

### 3.5 【R-05】AC18 的 8 类日志必须用**扫描件**才有 `ocr`

文本型合同链路没有 OCR 环节，自然只有 7 类（`pull/download/parse/extract/rule/save/write_comment`）。
AC18 要求"8 类 `log_type` 均有记录"，因此验收与测试都使用 **AP-003（扫描件）** 跑完整九步闭环，
得到 `['download','extract','ocr','parse','pull','rule','save','write_comment']`。文本型只有 7 类属**预期语义**，
已单独补一条用例把这一点固定下来，避免以后被误判为缺陷。

### 3.6 其他口径

- **非 `blocked` 任务重试 → 422 `VALIDATION_ERROR`**（见 §5 的 M5-A）；
- **重试不自动回写评论**：第 ⑨ 步是独立的 IF-17，重试只负责跑到 `done`（与九步闭环一致）；
- **规则阶段异常用 `AppError` 透传**：业务错误（如 `PARSE_REQUIRED`）不应被阶段级兜底吞成 `RULE_EXECUTION_FAILED`。

## 6. 遗留问题与 M6 入口条件

### 6.1 需要知悉的限制

| # | 事项 | 影响 |
|---|---|---|
| 1 | 重试**不会**重新下载已成功下载过的附件（`ensure_attachments` 复用库中记录） | "修复审批系统后重试"只在此前未成功下载过时才会真的重新拉取 |
| 2 | `retry_count` 只在**离开 `blocked`** 时累加（ST-01-02） | 与"点击重试次数"并非严格等价 |
| 3 | 全量测试约 3 分钟，其中 ~2 分钟是两次真实 OCR 推理 | 迭代请用 `-m "not slow and not llm"` |
| 4 | 日志正文里的合同片段**已按 500 字符截断** | 排查需要完整原文时看 `contract_parses.full_text` |
