## 3. 关键发现与实现决策

### 3.1 【R-01】模板关注点与命中的**下标错位**（实测踩出）

第一次冒烟时 AP-001 的评论第 4 条是：

```
4. 建议补充验收时间、验收方式及验收标准     ← 这是 R011（验收）的文字
证据：第2页 第9段。                        ← 这是 R003（自动续约）的证据
```

**根因**：构造 ``focus_by_rule``（``rule_code → 关注点文本``）时用**全量命中列表**（含 miss/uncertain）
去对齐关注点数组。R001–R011 里有 3 条 miss、若干 uncertain，于是 R003 拿到了 R011 的文案——
文字与证据行来自两个不同的风险。**对法务工具而言这是不可接受的**：审批人会以为"验收标准"的
证据是"合同期满自动续约"。

**修法**：一律按 ``active_hits``（仅 ``hit_status=hit``，等级降序）对齐，并补回归用例
``test_template_focus_aligned_with_active_hits``。

### 3.2 【R-02】关注点必须按 `rule_code` 与命中配对

评论模板要求每个编号关注点后面跟"证据：{position}"或"建议：{suggestion}"行。
若让 LLM 自由输出关注点数组（``["关注点1", "关注点2", ...]``），就无法可靠地知道
哪条关注点对应哪条命中——**错配会把不相关的原文位置当作证据展示**。

**决策**：提示词要求模型返回 ``[{"rule_code": "...", "text": "..."}]``，系统按 ``rule_code``
严格配对；认不出的 ``rule_code`` 直接丢弃（记 warning），未给出关注点的命中回落模板文案。
这样"LLM 措辞 + 系统证据"两者都对得上。

### 3.3 【R-03】`comment_logs` 的唯一索引与"追加不覆盖"冲突

DT-07 的 ``idempotency_key`` 是 ⭐UNIQUE（DT-00-05：唯一索引是幂等性的**最终保障**），
而 ST-02-02 又要求"每次状态变化**新增**一条 ``comment_logs``（追加，不覆盖）"。
同一个 ``(instance_id, review_id)`` 上两者无法同时成立——幂等键必须稳定，否则审批系统
会当成两条评论。

**取舍**（见 §5 的 M4-A）：

- ``comment_logs``：**一条逻辑评论一行**，``write_status`` 就地从 ``writing`` 更新为
  ``success``/``failed``。唯一索引即"禁止重复评论"的最终保障（FR-COM-02 / NF-03）；
- ``task_logs(log_type=write_comment)``：**每次尝试追加一条**，完整保留重试审计轨迹
  （FR-LOG-01 / FR-LOG-05）。

### 3.4 其他口径

- **无命中时不调用 LLM**：``overall=low`` 时摘要必须是规范文案
  "本次自动审查未发现明确的高风险或中风险条款。"，关注点必须为空数组——直接走模板，省一次调用；
- **FR-COM-06 短路优先于正文守卫**：已 ``success`` 的记录再次回写直接返回既有结果，
  不再校验正文——``success`` 是终态（ST-02-01），历史正文不该被今天的守卫推翻。
  用例因此选用了上一次为 ``failed`` 的任务来验证守卫；
- **FR-COM-07 守卫**：回写前校验正文"必须以免责声明结尾且不含替代人工决策的表述"，
  不合规则**拒绝回写**（宁可不写，也不把不合规正文写进审批系统）；
- **LLM 用途标签**：``complete_json(purpose=...)`` 区分 ``semantic_judge`` 与
  ``summary_generation``，满足 LM-17"记录调用用途"；
- **跨实例 review_id 拒绝**：``write_approval_comment(instance_id, review_id)`` 会校验
  ``review.task_id`` 与实例一致，避免把 A 合同的审查结果写进 B 合同的评论区。
