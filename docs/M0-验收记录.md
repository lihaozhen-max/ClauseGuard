## 5. 需要知悉的决策与偏离（请确认）

M0 期间遇到 3 处需要判断的地方，处理如下：

| # | 事项 | 处理 | 理由 |
|---|---|---|---|
| **M0-A** | `LLM_API_KEY` 在 SPEC CF-14 标为**必填**，但 LM-18 要求"Key 为空时系统必须仍能跑通 AC01–AC19" | 按 **LM-18** 实现：Key 为空时**自动**置 `llm_enabled=false` 并记降级告警，**不**启动失败 | 二者冲突时若按 CF-14 则无 Key 根本无法启动，与 LM-18 及设计 §9.3 的降级目标直接矛盾 |
| **M0-B** | 新增 `DB_ROOT_PASSWORD` 到 `.env` | 加入 `.env` / `.env.example`，并注明"仅 docker compose 使用，应用不读取" | MySQL 容器初始化与 healthcheck 需要 root 口令；SPEC CF-04 只列了应用连接用的账号 |
| **M0-C** | SPEC §5.4 只有 12 个业务错误码，但 NF-09 要求"接口错误必须返回 §5.3 统一结构" | 补充 2 个**框架级**错误码 `VALIDATION_ERROR`(422)、`INTERNAL_ERROR`(500)，业务码仍严格为那 12 个 | 参数校验失败与未捕获异常也必须走统一结构，且兜底响应体不得含堆栈 |

另外两处实现口径（已在代码注释中标注）：

- `approval_tasks → contract_parses` 建模为 **1..n**（`parses` 集合）。架构图 FIG-08 写作 1..1，
  但 DT-03 的唯一约束是 `UNIQUE(task_id, attachment_id)`，一个任务可挂多个附件、各产生一条解析记录，
  1..n 才能表达该约束。**如需严格 1..1，请指出，我改回单值关系。**
- `alembic` 已纳入依赖但 M0 **未接入迁移**：设计 §3.3 明确以 `database/schema.sql` 作为初始化建表路径，
  引入 alembic 迁移链会形成第二套 DDL 来源。**待确认是否需要在 M1 前补迁移基线。**
